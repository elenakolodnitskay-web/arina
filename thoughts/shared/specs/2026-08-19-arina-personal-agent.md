# Спецификация проекта Арина — нейроагент-персональный ассистент

Дата: 2026-08-19
Статус: Готово к планированию реализации — **при условии закрытия блокера** (см. «Предусловие для старта разработки»)

## Резюме

Арина — ИИ-агент в Telegram, который выступает для пользователя единым цифровым помощником в работе и личных делах, автоматически определяя, к какому контексту относится каждое сообщение, без ручного переключения режимов. Ключевая ценность — не отдельная функция (задачи, напоминания, документы по отдельности уже решены десятками существующих продуктов), а то, что агент помнит контекст между обращениями и не заставляет объяснять всё заново. Целевая аудитория MVP — узкий круг приглашённых русскоязычных пользователей (закрытая бесплатная бета), цель MVP — не выручка, а проверка единственной непроверенной гипотезы: возвращаются ли люди к агенту, который «помнит».

Эта спецификация — результат трёхшагового процесса: идея (`idea.md`) → исследование конкурентов (`research.md`) → жёсткая критика идеи и фактчекинг исследования (`критика.md`). Объём MVP в этой спецификации **сознательно урезан** относительно первоначальных решений интервью — по итогам критики от независимого агента-рецензента, с которой автор согласился (см. «Что изменилось после критики»).

## Предусловие для старта разработки (блокер)

Проект Арина использует ту же инфраструктурную зависимость, что и соседний проект автора Aiy: доступ к Claude через OpenRouter из российского хостинга (Beget) идёт через релей на Cloudflare Worker. На момент написания этой спецификации в Aiy эта зависимость **не стабилизирована в проде** («релей для Telegram, OpenRouter пока заблокирован» — зафиксировано в git-истории Aiy). Разработку Арины на этой же инфраструктуре запускать не следует, пока релей не работает стабильно в Aiy — иначе новый продукт наследует уже наблюдаемый, а не гипотетический риск отсутствия работающего ядра. Это предусловие, а не задача этого проекта — фиксируется здесь как блокер для отслеживания.

## Проблема

Люди используют разрозненные инструменты: таск-трекер для работы, заметки для быта, мессенджеры для переписки, календарь для дедлайнов. Между ними нет связи, и человеку приходится самому держать в голове полную картину.

**Ограничение, зафиксированное после критики**: сама по себе боль «разрозненность инструментов» не подтверждена внешними пользователями — только личным опытом автора идеи. Функции «список дел + напоминания» по отдельности не являются рыночной новизной (Todoist, TickTick, Skeddy Bot и десятки других решают то же самое годами — см. `research.md`). Единственная содержательная гипотеза, которую стоит проверять, — способна ли долговременная память о пользователе (а не факт наличия списка задач) реально снизить трение по сравнению с существующими инструментами настолько, чтобы люди возвращались. MVP спроектирован так, чтобы проверить именно эту гипотезу — дёшево и без искажающих факторов (без биллинга, без лишних каналов).

## Критерии успеха MVP

- **Основная метрика — удержание (retention)**, не число регистраций и не выручка. Смотрим, возвращаются ли приглашённые пользователи к агенту через 1/2/4 недели после первого использования.
- Продукт корректно ведёт задачи/напоминания и удерживает контекст между разговорами без повторного объяснения пользователем.
- Автоматическая классификация «работа / личное» ощущается пользователем как полезная, а не как источник раздражающих ошибок — измеряется через частоту использования ручной коррекции классификации.
- Ни один платящий пользователь не пострадал от утечки/потери персональных данных (в MVP нет платящих пользователей, но требование к защите данных то же).

## Что изменилось после критики (сознательные отступления от первоначальных решений интервью)

| Было решено в интервью | Что изменено в этой спецификации | Почему |
|---|---|---|
| Продукт для многих с первого дня, мультитенантный SaaS | Изоляция данных остаётся (нужна для 152-ФЗ в любом случае), но без биллинг-инфраструктуры и тарифных планов — закрытая бета по приглашениям | Спрос не подтверждён, инфраструктура «на рост» без пользователей — потраченное время не на то |
| Telegram + веб сразу, один аккаунт на двух платформах | Только Telegram в MVP | Два интерфейса = отдельная система авторизации, синхронизация состояния, отдельный push-стек — объём сопоставим с ещё одним Aiy |
| Email+пароль как основа, Telegram — привязка | Telegram ID как единственный идентификатор пользователя (как в Aiy) | Упрощение возможно и оправдано раз веба и биллинга нет в MVP |
| Платная подписка с первого дня + бесплатный пробный период | Бесплатная закрытая бета, без оплаты | Биллинг с первого дня искажает замер retention (нельзя отличить «не понравилось» от «закончился триал») |
| Гибридная память: структурированная БД + семантический (векторный) поиск | Структурированная БД (задачи/заметки) + скользящее текстовое summary диалога, БЕЗ векторного поиска | Тюнинг retrieval без реальных данных пользователей — подгонка вслепую, почти гарантированно потребует переделки |
| Автоматическая LLM-классификация работа/личное, без ручного переключения | То же, но добавлена возможность пользователю быстро поправить неверную классификацию | При типичной точности классификации 85–92% без коррекции — заметная доля сообщений теряется в «не туда» без возможности исправить |
| Написание документов/писем с нуля по описанию | То же + явный шаг подтверждения текста пользователем перед тем, как считать его готовым к использованию | Репутационный риск ошибки в письме ложится на пользователя, не на бота |

Всё остальное из интервью (русскоязычная аудитория, OpenRouter/Claude, Python, Beget, шифрование и 152-ФЗ, удаление данных по запросу, реактивная обработка сбоев LLM, разовые+повторяющиеся напоминания) сохранено без изменений.

## Пользователи

- **Аудитория MVP**: узкий круг приглашённых русскоязычных пользователей (закрытая бета, не публичная регистрация) — размер группы определяется на этапе запуска
- **Технический уровень**: разный, интерфейс рассчитан на обычного пользователя Telegram, без специальных знаний
- **Владелец продукта**: ведёт разработку в режиме ИИ-ассистированной разработки (как Aiy), без выделенной команды

## Путь пользователя (MVP)

1. Пользователь получает приглашение и открывает Telegram-бота
2. Короткий опрос-анкета при первом запуске (чем занимается, какие проекты/сферы жизни ведёт) — даёт агенту стартовый контекст
3. Пользователь общается с ботом в свободной форме — задача, напоминание, мысль, просьба написать письмо
4. Агент через LLM определяет, к какому контексту (работа/личное) относится сообщение, и сохраняет соответствующим образом; под сообщением — способ быстро поправить, если классификация неверна
5. Задачи и напоминания (разовые и повторяющиеся) сохраняются в структурированном виде; агент присылает проактивные push-напоминания в Telegram в заданное время
6. Свободный контекст (мысли, договорённости, детали) хранится как текстовые записи + скользящее summary диалога, к которому агент обращается в следующих разговорах
7. При просьбе написать документ/письмо — агент генерирует текст с нуля по описанию и явно просит пользователя подтвердить/отредактировать перед использованием
8. Пользователь может в любой момент запросить полное удаление своих данных

### Обработка ошибок и нештатных ситуаций
- LLM (OpenRouter/релей) недоступен → понятное сообщение об ошибке на русском, предложение повторить попытку, без зависания диалога
- Неверная классификация работа/личное → пользователь поправляет через простую команду/кнопку, агент подтверждает исправление
- Сгенерированный документ/письмо не устроил → пользователь может попросить переформулировать, текст никогда не считается «отправленным от имени бота», финальное решение — за пользователем

## Функциональные требования

### Must Have — MVP (v1)
- Telegram-бот, весь текст на русском языке
- Идентификация пользователя по Telegram ID (без отдельной регистрации email/пароль)
- Закрытая бета: доступ только по приглашению, без биллинга
- Короткий опрос-онбординг при первом запуске
- Задачи и напоминания — разовые и повторяющиеся, естественный язык для постановки
- Проактивные push-напоминания через Telegram
- Автоматическая LLM-классификация сообщений на «рабочий» / «личный» контекст
- Механизм ручной коррекции классификации (команда или инлайн-кнопка «это не туда»)
- Память: структурированная БД для задач/заметок + скользящее текстовое summary диалога для удержания контекста между сессиями (без векторного поиска)
- Написание документов/писем с нуля по словесному описанию, с явным шагом подтверждения перед использованием текста
- Шифрование персональных и рабочих данных в БД, соответствие 152-ФЗ
- Команда полного удаления всех данных пользователя по запросу (аналог `/delete_my_data` из Aiy)
- LLM — Claude через OpenRouter, доступ через Cloudflare-релей (переиспользование инфраструктуры Aiy — **только после того, как релей стабилизирован в Aiy**, см. «Предусловие»)
- При недоступности LLM — сообщение об ошибке и предложение повторить

### Should Have — v1.1 (после проверки retention-гипотезы на закрытой бете)
- Веб-интерфейс (просмотр/планирование), привязка к тому же аккаунту через Telegram Login Widget
- Платная подписка через ЮKassa с бесплатным пробным периодом — **только после решения юридических вопросов**: юрлицо/ИП для приёма платежей, публичная оферта, фискализация по 54-ФЗ, политика возвратов
- Web push как второй канал напоминаний (вместе с веб-интерфейсом)
- Семантическая (векторная) память поверх накопленных реальных данных пользователей — тюнинг chunking/top-k/ранжирования на реальных диалогах, а не вслепую
- Расчёт и публикация юнит-экономики (стоимость LLM-вызовов на пользователя/месяц vs цена подписки) — предусловие для запуска биллинга

### Should Have — v1.2
- Интеграция с внешним календарём (Google Calendar) — устраняет главное противоречие MVP («единая память», но события календаря агенту не видны)
- Работа с входящими документами (анализ PDF/Word/Excel), не только генерация с нуля
- Слоистая агрегация памяти (день → неделя → месяц → профиль пользователя) вместо плоского лога/summary — по примеру архитектуры Iva (см. `research.md`)

### Nice to Have — v2+
- MCP-интеграция для подключения сторонних ИИ-клиентов к данным агента (подтверждённый паттерн у OK, Bob! — см. `research.md`)
- Персональный CRM-блок для рабочего контекста (контакты, договорённости с клиентами) — по примеру Iva
- Открытая регистрация вместо закрытой беты, полноценная мультитенантная инфраструктура «на рост»
- Полноценная админ-панель, поддержка пользователей на масштабе
- Тиражирование каркаса агента для других пользователей с индивидуальным наполнением (изначальная идея «потенциала развития»)

## Техническая архитектура

### Стек
- **Python** — бэкенд, тот же язык, что и Aiy
- **python-telegram-bot** — интерфейс Telegram
- **PostgreSQL + SQLAlchemy + Alembic** — хранение задач, заметок, summary диалогов, профиля пользователя
- **cryptography (Fernet)** — шифрование персональных/рабочих данных (аналог `db/crypto.py` из Aiy)
- **OpenRouter (модель Claude)** через Cloudflare Worker релей — классификация сообщений, генерация ответов и документов, суммаризация диалога
- **Планировщик задач** (например APScheduler) — доставка разовых и повторяющихся напоминаний

### Хостинг и данные
- Beget (переиспользование опыта Aiy), VPS в России — требование локализации персональных данных по 152-ФЗ
- Шифрование хранимых персональных/рабочих данных, механизм полного удаления по запросу

### Компоненты, требующие отдельного внимания
- **Точность LLM-классификации работа/личное** — не разовая настройка, а процесс: нужен набор тестовых сообщений (включая неоднозначные — «созвон с Димой в 19») для проверки промпта перед запуском беты, аналогично калибровке с астрологом в Aiy, но здесь — калибровка на диалогах, а не на астрономических расчётах
- **Скользящее summary диалога** — нужно определить окно/частоту пересуммаризации, чтобы не терять важные детали при потере старого контекста (временное решение до появления полноценной семантической памяти в v1.1)

## Безопасность и соответствие требованиям

- Гео-аудитория — Россия → 152-ФЗ «О персональных данных»
- Требование локализации: данные пользователей хранятся на серверах в РФ
- Шифрование хранимых персональных/рабочих данных
- Механизм удаления данных пользователя по запросу
- В MVP нет денежных операций — вопросы фискализации (54-ФЗ), оферты и юрлица для приёма платежей откладываются до v1.1 вместе с биллингом, но должны быть закрыты **до**, а не во время реализации оплаты

## Монетизация

- **В MVP (v1) монетизации нет** — закрытая бесплатная бета, чтобы честно измерить retention без искажающего фактора оплаты
- С v1.1: платная подписка через ЮKassa (карты, СБП) с бесплатным пробным периодом — при условии решения юридических вопросов и расчёта юнit-экономики
- Ориентиры по ценам конкурентов (Claw Bot — 1799 ₽/мес, AICombo — заявлено 500 ₽/мес) требуют ручной перепроверки перед использованием — фактчекинг (`критика.md`) показал, что цифры AICombo не подтвердились при прямой проверке актуального сайта

## Принцип принятия решений (голос агента)

- Агент по умолчанию не решает за пользователя — советует, предлагает варианты, подсвечивает важное; финальное решение всегда за пользователем
- Исключение — то, что пользователь явно делегировал агенту (например, напоминания по расписанию)
- Сгенерированные документы/письма — всегда черновик, требующий подтверждения пользователя, а не готовый к отправке текст

## Вне рамок MVP (сознательно исключено)

- Веб-интерфейс — v1.1
- Платная подписка / биллинг — v1.1, после закрытия юридических вопросов
- Семантическая (векторная) память — v1.1, после накопления реальных данных
- Интеграция с внешним календарём/таск-трекерами — v1.2
- Анализ входящих документов (только генерация с нуля в MVP) — v1.2
- MCP, CRM-блок, открытая регистрация, полноценная мультитенантность «на рост», админ-панель — v2+

## Открытые вопросы для этапа реализации

- **Блокер**: стабилизация релея OpenRouter в проде Aiy — без этого старт разработки Арины откладывается
- Конкретный формат UX для ручной коррекции классификации (команда vs инлайн-кнопка под каждым сообщением)
- Размер и состав группы закрытой беты, критерии отбора приглашённых пользователей
- Окно/частота пересуммаризации скользящего summary диалога
- Набор тестовых диалогов для калибровки промпта LLM-классификации перед запуском беты
- Юрлицо/ИП для будущего приёма платежей, конкретная оферта, схема фискализации по 54-ФЗ (к моменту v1.1)
- Канал привлечения пользователей закрытой беты (сейчас не определён)

## Приложения: результаты исследования и критики

Полное исследование конкурентов — `research.md`, критический разбор идеи и фактчекинг исследования — `критика.md`. Ключевые выводы:
- Надёжные архитектурные ориентиры: слоистая память Iva (Memory Tree: день→неделя→месяц→профиль), модель «три уровня доступа» + прозрачное объяснение zero-knowledge шифрования у MyGemini Zero, лимиты free-тарифа и MCP-интеграция у OK, Bob!
- Не использовать без дополнительной проверки: цифры монетизации AICombo (не подтвердились при фактчекинге), репутационные показатели Skeddy Bot (13 тыс. пользователей, 90% отзывов, год запуска — источники не найдены), профиль AI Secretary целиком (основан на паре SEO-каталогов)
- Ближайший прямой конкурент — OK, Bob! (RU-рынок, Telegram, задачи+ИИ+голос) — точные тарифы стоит сверить вручную перед финализацией собственного прайсинга в v1.1
- Критика идеи выявила, что объём, согласованный в интервью, фактически представлял собой 4-5 отдельных MVP, слитых в один релиз — эта спецификация — результат сознательного сокращения объёма до одного проверяемого MVP
