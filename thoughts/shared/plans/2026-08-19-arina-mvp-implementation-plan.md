## Предусловие

Как зафиксировано в спецификации и `Plan.md`: релей к OpenRouter через Cloudflare
Worker должен быть стабилизирован в проде соседнего проекта Aiy **до** того, как Фаза 3
(и всё, что от неё зависит) начинается здесь. Это внешняя зависимость, не задача этого
плана — план фиксирует её как блокер, а не пытается её решить.

## Принципы плана

- Фазы упорядочены так, чтобы всё, что технически не зависит от LLM (окружение, БД,
  каркас бота, онбординг), можно было делать уже сейчас, не дожидаясь блокера.
- Каждая фаза заканчивается рабочим, тестируемым состоянием — не «наполовину сделанным».
- Шифрование персональных/рабочих данных закладывается с Фазы 1, а не добавляется
  задним числом — переделка модели данных под шифрование постфактум дороже, чем
  сразу писать `db/crypto.py` до первой миграции.
- Точность LLM-классификации — процесс, а не разовая задача (см. критику, п.4а):
  калибровочный набор диалогов закладывается в Фазу 3 как часть работы, а не как
  дополнение после запуска.

## Фаза 0 — Окружение и конвенции

**Цель**: воспроизводимое окружение разработки, соответствующее конвенциям `CLAUDE.md`.

Задачи:
- Инициализировать git-репозиторий, `.gitignore` (исключить `venv/`, `.env`, `*.db`)
- `venv/` в корне проекта, `requirements.txt` с зафиксированными версиями:
  `python-telegram-bot>=20`, `openai`, `SQLAlchemy`, `alembic`, `psycopg2-binary`,
  `cryptography`, `APScheduler`, `pydantic-settings`, `pytest`
- `config.py` — единая точка чтения конфигурации через `pydantic-settings`
  (`.env`: `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, `OPENROUTER_BASE_URL`,
  `OPENROUTER_API_KEY`, `FERNET_KEY`, `ALLOWED_USER_IDS`)
- Скелет каталогов из `CLAUDE.md` (`db/`, `llm/`, `core/`, `bot/handlers/`, `tests/`)
  с пустыми `__init__.py`
- `pytest` настроен, один тривиальный тест на загрузку `config.py` — чтобы CI/локальный
  прогон был осмысленным с первого коммита

**Готово, когда**: `pytest` зелёный, `python -m bot.main` стартует и падает только на
отсутствии реального токена (ожидаемо на этом этапе).

## Фаза 1 — Хранилище данных

**Цель**: модель данных и шифрование готовы до того, как в БД попадёт первая строка
реальных данных пользователя.

### Схема данных (`db/models.py`)

- **User**: `telegram_id` (уникальный, идентификатор пользователя вместо email/пароля —
  решение спецификации), `created_at`, `onboarding_completed`, `profile_summary`
  (зашифрованный текст — ответы онбординга)
- **Task**: `user_id`, `title` (зашифровано), `context` (`work` / `personal`),
  `due_at`, `recurrence_rule` (nullable — разовая задача, если пусто), `status`
  (`active` / `done` / `cancelled`), `created_at`
- **Note**: `user_id`, `content` (зашифровано), `context` (`work` / `personal`),
  `created_at` — свободные мысли/договорённости, не оформленные как задача
- **DialogSummary**: `user_id`, `context` (`work` / `personal` — раздельное summary
  по контекстам, см. спецификацию «хранит раздельно, но незаметно для пользователя»),
  `summary_text` (зашифровано), `updated_at`, `message_count_since_update`

Решение: **раздельные поля/строки `context` в Task/Note/DialogSummary**, а не отдельные
таблицы `work_*` / `personal_*`. Проще миграции, проще единый запрос «покажи всё за
неделю», а изоляция контекстов на уровне бизнес-логики (`core/`), не схемы БД.

### Шифрование (`db/crypto.py`)

Аналог `db/crypto.py` из Aiy: Fernet-шифрование на уровне полей перед записью,
расшифровка при чтении. Ключ — `FERNET_KEY` из `config.py`, не хардкодить, не логировать.
Шифруются: `profile_summary`, `Task.title`, `Note.content`, `DialogSummary.summary_text`.
Не шифруются (не персональные/не содержательные): `telegram_id`, `context`, статусы,
временные метки — нужны для запросов и индексов, шифрование сделало бы их
непригодными для `WHERE`/`ORDER BY`.

### Миграции

Alembic с первого коммита в этой фазе, не после. `db/session.py` — фабрика сессий
SQLAlchemy, единая точка подключения к PostgreSQL.

**Готово, когда**: `alembic upgrade head` создаёт схему на чистой PostgreSQL, юнит-тест
пишет и читает зашифрованную запись и получает исходный текст обратно.

## Фаза 2 — Каркас Telegram-бота (без LLM)

**Цель**: бот отвечает реальным пользователям в Telegram, проходит онбординг,
но ещё не обращается к LLM — блокер (Фаза 3) сюда не заходит.

Задачи:
- `bot/main.py` — точка входа, `Application` из `python-telegram-bot`, регистрация
  хендлеров
- **Whitelist по приглашению**: `ALLOWED_USER_IDS` (или отдельная таблица приглашений,
  если список динамический) — `/start` от чужого Telegram ID получает вежливый отказ
  на русском, не создаёт запись `User`
- `bot/states.py` + `bot/handlers/onboarding.py` — короткий опрос при первом запуске
  (чем занимается, какие проекты/сферы ведёт), результат пишется в
  `User.profile_summary`
- Заглушка `/delete_my_data` уже на этом этапе (без реальной LLM-логики она безопасна
  реализовать сразу — просто каскадное удаление строк пользователя), чтобы не забыть
  её на фоне более сложных фаз

**Готово, когда**: реальный пользователь в Telegram проходит `/start` → онбординг →
видит подтверждение «профиль сохранён», данные лежат в БД зашифрованными.

## Фаза 3 — LLM-ядро

**Цель**: рабочий, протестированный доступ к модели через релей + калиброванная
классификация работа/личное.

- `llm/client.py` — обёртка над `openai` SDK с `base_url` на Cloudflare Worker релей,
  retry с экспоненциальной паузой на сетевые сбои, понятная ошибка на русском при
  исчерпании попыток (спецификация: «понятное сообщение, без зависания диалога»)
- `llm/classify.py` — промпт классификации сообщения на `work` / `personal`, возвращает
  контекст + уверенность
- `tests/calibration/` — набор тестовых сообщений **до** запуска беты, включая заведомо
  неоднозначные («созвон с Димой в 19» — рабочее или личное?), см. открытый вопрос
  спецификации. Замер точности на этом наборе — условие перехода к Фазе 4, не
  формальность

**Готово, когда**: калибровочный набор проходит с точностью, зафиксированной как
приемлемая перед стартом беты (порог обсуждается по факту первых прогонов — не задан
заранее произвольным числом), retry-логика покрыта тестом на симулированном сбое сети.

## Фаза 4 — Свободный чат и коррекция классификации

- `bot/handlers/free_chat.py` — приём произвольного сообщения → `llm/classify.py` →
  запись в `Note` с проставленным `context`
- Инлайн-кнопка «это не туда» под каждым классифицированным сообщением — исправляет
  `context` задним числом, бот подтверждает исправление текстом на русском
  (спецификация: механизм ручной коррекции обязателен из-за типичной точности
  классификации 85–92%)

**Готово, когда**: неверно классифицированное сообщение можно поправить одной кнопкой,
исправление видно в БД.

## Фаза 5 — Задачи и напоминания

- `core/tasks.py` — разбор естественно-языковой формулировки в структурированную
  задачу (срок, повтор) через LLM-вызов с строгим форматом ответа (JSON)
- `core/scheduler.py` — APScheduler с job store в той же PostgreSQL (переживает
  перезапуск процесса — важно для продакшена, in-memory job store здесь не подходит)
- `bot/handlers/tasks_flow.py` — создание/просмотр/отмена задач, проактивная отправка
  напоминания в заданное время через `bot`

**Готово, когда**: разовое и повторяющееся напоминание, поставленное свободной фразой,
реально приходит в Telegram в заданное время после перезапуска процесса бота.

## Фаза 6 — Память и скользящее summary диалога

- `core/dialog_summary.py` — по достижении порога `message_count_since_update`
  (конкретное число — открытый вопрос спецификации, зафиксировать по итогам ручного
  тестирования в этой фазе, не гадать заранее) пересуммаризирует последние сообщения
  через LLM и обновляет `DialogSummary.summary_text`, раздельно по `context`
- При каждом новом обращении пользователя — текущее summary подмешивается в промпт
  как контекст (то, что заменяет полноценную память до v1.1)

**Готово, когда**: во втором разговоре, начатом на следующий день, бот корректно
ссылается на факт, упомянутый накануне, без повторного объяснения пользователем.

## Фаза 6.5 — Разговорный ответ

*Добавлено 2026-08-19, в ходе работы над Фазой 6 — исходный план фаз 0-9 не включал
отдельную фазу для содержательного ответа бота на сообщение пользователя (Фаза 4
только классифицирует и подтверждает сохранение). Спецификация (`thoughts/shared/specs/2026-08-19-arina-personal-agent.md`,
раздел «Технические детали → Стек») с самого начала предполагала «генерацию ответов»
через OpenRouter — формально это была пропущенная фаза, а не новая функция.
Обнаружено и явно подтверждено пользователем при обсуждении Фазы 6.*

**Цель**: бот отвечает на свободное сообщение по существу, а не просто подтверждает
классификацию — используя скользящее summary диалога (Фаза 6) как контекст.

- `llm/reply.py` — `generate_reply(text, context, summary)`: генерирует содержательный
  ответ на сообщение пользователя с учётом контекста (работа/личное) и текущего
  `DialogSummary.summary_text`, если он есть
- `bot/handlers/free_chat.py` — вместо технического «Записал как «...»» бот присылает
  содержательный ответ от `generate_reply`; инлайн-кнопка «Это не туда» остаётся под
  этим же сообщением (механизм коррекции классификации из Фазы 4 не меняется)

**Готово, когда**: во втором разговоре, начатом на следующий день, бот корректно
ссылается на факт, упомянутый накануне, без повторного объяснения пользователем (этот
критерий перенесён из Фазы 6, поскольку по факту требует именно разговорного ответа,
а не просто наличия готового summary).

## Фаза 7 — Документы и письма

- `llm/documents.py` — генерация текста письма/документа с нуля по словесному описанию
- `bot/handlers/documents_flow.py` — после генерации бот явно просит подтвердить/
  отредактировать, сгенерированный текст никогда не помечается и не отправляется как
  «финальный» автоматически (спецификация: репутационный риск — на пользователе, но
  только после его подтверждения)

**Готово, когда**: сгенерированный черновик требует явного действия пользователя
(«подтвердить» / «переформулировать») прежде, чем считается готовым.

## Фаза 8 — Безопасность и 152-ФЗ (сквозная, добавляется по ходу Фаз 1-7)

- Аудит: ни одно поле с персональными/рабочими данными не попадает в логи в открытом

- `/delete_my_data` из Фазы 2 — расширить до полного каскадного удаления по всем

- Данные размещаются на Beget (РФ) — требование локализации 152-ФЗ, проверить при

## Фаза 9 — Закрытая бета

- Список приглашённых пользователей (размер и критерии — открытый вопрос спецификации,
  решается отдельно от технической реализации)

- Запуск замера retention (1/2/4 недели) — единственная метрика успеха MVP

## Тестирование (сквозное правило)

Каждый новый модуль с логикой сопровождается тестом в `tests/` в том же коммите
(правило `CLAUDE.md`). Отдельно: `tests/calibration/` для классификации (Фаза 3) —
не юнит-тесты в обычном смысле, а фиксированный набор диалогов с ожидаемой
классификацией, прогоняется вручную/в CI перед каждым изменением промпта классификации.
